# 学业负荷雷达

一个面向大学生的学业任务负荷与截止日期风险分析工具。

本次验收使用2026-10-30样例，先运行 `python -B -m tools.preview_acceptance --extra-hours 2`，或双击根目录的“运行验收样例.cmd”，再打开终端输出的网址。该入口使用临时数据库、24条历史与11条当前虚构任务，额外日投入上限为2h；停止后再启动即可重置。日期固定，其他日期运行时数值会变化。程序更新后请重启服务并刷新页面。

验收与评测使用的虚构 CSV 分别放在 `examples/acceptance/` 和 `examples/evaluation/`。

## 运行

在项目目录执行：

```powershell
python -m app.main
```

然后打开 <http://127.0.0.1:8000>。

本地默认数据文件位于系统临时目录。要指定项目内的数据目录，可设置 `ACADEMIC_LOAD_RADAR_DATA`；公网部署必须使用托管平台的持久化目录。

## 当前功能

- 创建、删除和标记完成任务。
- 可直接更新进行中任务的累计投入工时与完成比例。
- 设置工作日/周末可用时间和缓冲比例。
- 根据可用工时、截止日期、优先级与全部待办任务计算组合风险。
- 用 EDF（最早截止期优先）模拟排程，显示建议顺序、预计完成日和截止前工时缺口。
- 当截止前容量不足时，比较增加投入、保住关键任务和完成更多任务三种方案，展示推荐依据、原范围保留任务与需调整任务。
- 根据课程与标题关键词关联可靠历史任务，展示匹配依据和实际工时，并用于校准当前预测；可从当前任务跳转查看历史记录。
- 为剩余工时预测显示高/中/低可信度，说明当前判断的数据基础。
- 在仪表盘显示下一步行动、高风险任务、预计工时和风险解释，支持筛选与中英文多关键词搜索。
- 跟踪任务实际用时，并区分提前、按时和逾期完成。
- 单条补录历史任务，或通过 CSV 批量导入过去的任务。
- 单条录入进行中任务，或通过 CSV 批量导入已经开始但尚未完成的任务。
- 进行中任务支持已投入工时和当前进度，风险分析会按剩余工时估算负荷。
- 查看近 30 天按时完成率、估时偏差和临近截止日期效率变化。
- 根据至少 5 个已完成任务给出缓冲比例调整建议。
- 本地使用 SQLite 保存数据，普通进程重启后通常仍可保留（默认位于系统临时目录；部署时可用 `ACADEMIC_LOAD_RADAR_DATA` 指定目录）。Render Free 的临时文件系统不保证跨实例重启保留数据。

## 简报与导出

首页“负荷简报”支持生成本地规则简报、请本机 Codex 整理简短建议，以及复制材料给当前 Codex 对话。报告包含剩余工时、共享容量缺口、前三项行动与取舍方案，支持导出 TXT、Markdown、JSON依据及可打印HTML；PDF通过浏览器打印另存，不是服务端直接生成。

自动调用使用本机 `codex exec` 的独立临时会话，不会续写或接管当前聊天。需安装并登录 Codex CLI；未在PATH时可由服务端环境变量 `RADAR_CODEX_BIN` 指定可执行文件。调用前需确认发送分析摘要和最早最多20条当前任务，可能使用登录账户额度。全体任务仍参与算法计算。工时、风险与可行性由本地算法确定，AI只提供解读；失败会明确显示，不冒充AI成功。[官方非交互模式说明](https://learn.chatgpt.com/docs/non-interactive-mode)提供了这一调用方式。

Windows本地服务会依次检查`RADAR_CODEX_BIN`、PATH和Codex桌面应用的本机安装目录，兼容桌面应用已安装CLI但普通终端PATH中不可见的情况。显式指定的路径失效时会如实报不可用，不改用其他安装。重新展开简报区域会重新检测；升级服务端代码后仍须重启Python服务，再刷新网页。CLI登录沿用本机已登录状态，不把登录凭据放入网页或项目文件。

临时桥接仅允许服务绑定在回环地址，并校验请求来源及报告请求令牌；不通过公网部署开放本机账户调用。报告最多在进程内保留20份、保留24小时，服务重启后失效。任务、设置或日期变化后标记旧快照，导出不更新任务数据。

## 完整完成与部分交付

每张任务卡片都显示重要程度。完整交付显示提前／按时／逾期完整完成；选择“部分交付后结束”则填写大于0且小于100、最多两位小数的实际交付比例与可选说明。开启跟踪时还需填写此次交付累计实际用时；关闭时不代填预计工时。

例如交付70%后结束，卡片保留70%，标明未交付30%；不再安排未来工时，但不算作完整完成，不进入完整完成按时率和完整工时校准。逾期部分交付单独显示。若之后继续剩余内容，应另建后续任务，不能改写原交付结果。

原型数据库使用 `status=done` 表示已结束，以新增 `completion_scope=full/partial` 区分结果，`closure_note` 保存说明。现有记录默认full，不推测哪些旧记录其实只交了一部分。新增字段不删除原数据；已在运行的服务必须重启后再刷新页面，不能让新版页面连接旧后端。

部分交付的用时单独记录。个性化误差模型属于后续工作。

## 跟踪模式

开启跟踪模式后，点击“完整完成”会记录实际用时。系统会以截止日前 24 小时作为默认的“提前完成”阈值，并在 `/api/insights` 返回滚动窗口统计。临近截止日期的效率提升只作为解释性指标，不会直接替用户降低缓冲比例。

历史任务 API 为 `POST /api/tasks/history`，批量导入 API 为 `POST /api/tasks/import`。CSV 至少需要这些字段：`title`、`course`、`due_date`、`completed_at`、`estimated_hours`、`actual_hours`、`data_precision`；`started_at` 和 `stress_level` 可选。

进行中任务 API 为 `POST /api/tasks/ongoing`，批量导入 API 为 `POST /api/tasks/ongoing/import`。CSV 字段为：`title`、`course`、`due_date`、`started_at`、`estimated_hours`、`spent_hours`、`progress_percent`、`priority`、`data_precision`、`stress_level`。其中 `estimated_hours` 是预计总工时，`spent_hours` 是已经投入的工时，`progress_percent` 必须小于 100。示例文件为 `sample_ongoing_tasks.csv`。

批量处理已填写任务使用 `POST /api/tasks/batch/process`。它会一次重新处理数据库中全部任务，汇总剩余工时、风险分布、组合超载截止日期、排程缺口、最高风险任务和前三项行动建议。前端“任务风险”区域中的“重新计算”按钮会显示这份汇总结果。

批量处理和 `GET /api/dashboard` 同时返回 `tradeoff_plan`。2026年10月16日调整取舍目标：不再用“少调整几个重要任务”代替“保住重要交付”。现在逐个检查截止日期，先遵守已设交付底线，再从低、中、高重要度依次让出可调整工时，按高／中／低重要度逐级尽量减少原期限外工时；同重要度时参考期限、当前进度及可调整量。允许多调整几项低重要度任务，不为减少调整数量而大幅压缩重要任务。`priority_loss_hours` 显示各重要度的期限外工时；`high_priority_shortfalls` 给出即使先让出较低重要度可调整工时，重要任务仍无法按原期限完整交付的节点。

添加、补录和每张待处理任务卡片的“交付约束”可设置 `must_complete`（必须按原范围按时完整交付）与 `minimum_delivery_percent`（整个任务的最低交付比例，0–100、最多两位小数，留空为未知）。必须完整完成时保护全部剩余工时；否则按 `剩余工时 × max(0, 最低交付比例−当前进度) / (100−当前进度)` 换算至少应保留工时，向上取到0.01小时。不把已经完成的比例再次计入未来工时。比例只是线性工时近似，不能识别具体核心内容；未填不代表没有核心范围，所有缩减、延期必须本人确认。约束只限制建议，不会阻止如实记录实际的部分交付结果。

底线本身超出期限容量时，`unresolved_checkpoints` 列出冲突、缺口与相关任务，取舍方案 `feasible=false`。若额外投入也不足，则 `recommended_strategy=null`，明确没有满足约束的方案，不自动放弃必交任务或降低底线。`requires_confirmation=true` 表示仅为容量可排入的待协商情景，不保证对方接受缩减或延期。`PUT /api/tasks/{id}` 可单独提交这两个字段，不与进度或状态混合保存；进行中CSV兼容原格式，并可增加同名可选列（`must_complete` 用true/false或1/0）。升级新增字段默认“不标记必交／核心比例未知”，不会推断或覆盖旧记录。正式实验1／2提交文档不随本次实现变更自动改写；重启服务后数据库才会执行兼容升级。

## 多方案比较与推荐

超载时，`tradeoff_plan.strategies` 返回三种方案，`recommended_strategy` 和 `recommendation_reason` 返回建议选择及理由。点击首页方案卡片可以查看完整保留任务、执行顺序、调整工时和适用条件。

| 方案 | 方法 | 含义 |
|---|---|---|
| `extra_effort` 增加投入 | 逐个截止日期求补齐缓冲后缺口的最小均匀额外日工时 | 额外投入仍扣除缓冲，且不能超过用户设置的日上限或每日 24 小时的容量边界；已有逾期任务时不可恢复原期限 |
| `protect_important` 保住重要交付 | 交付底线＋逐截止日期的分级工时调整 | 先保护明确底线，再尽量少损失高重要度工时；较低重要度可让出更多任务，不能把调整数量少当作保护充分 |
| `finish_more` 完成更多任务 | 先预留全部核心底线，再对剩余工时运行最长项移出选择 | 最大化完整按期完成数，未完整保留任务也不能突破已设底线；底线冲突时明确不可行 |

推荐规则依次为：额外工时能在用户设定上限内补齐全部缺口，则建议增加投入；否则，底线冲突时不推荐虚假可行方案；底线可满足时，只有“多完成”不增加高重要度期限外工时、不减少其完整完成数且总完成数更多，才建议多完成，其余建议保住重要交付。该规则是当前产品的明确决策策略，尚未经过目标用户试验调优，不会自动修改任务范围、期限或进度。

“我的可用时间”中的 `max_extra_daily_hours` 默认 0，范围 0–8 小时。它只供情景比较，不改变基础容量和首页原计划的风险结论。所有任务假定今天已可开始、互不依赖、可分段执行，截止日期按整日计算；暂不处理前置依赖和日内时间段。完成数算法依据见 [Moore-Hodgson 正确性论文](https://arxiv.org/abs/2104.06210)。

## 关键词检索与历史关联

`GET /api/tasks/search?q=数据库%20报告` 返回同时匹配“数据库”和“报告”的当前或历史任务，检索字段为标题和课程名称。标题命中优先，支持大小写和全角英文归一化；关键词用空格分隔，最多 200 个字符。检索没有修改或建立永久关系，关联在每次分析时重新计算。

历史关联使用标题 TF-IDF 余弦相似度（中文相邻双字、英文词）与同课程信号：`匹配分 = 0.65 × 标题相似度 + 0.35 × 同课程`。分数至少 0.4 的前 5 项可靠已完成记录进入 `similar_history`，显示共享词句、课程、预计/实际工时和数据精度。仅同课程但标题无关联的记录不会入选，粗略记录不用于校准。匹配分不是难度相同的概率，也不具备同义词和语义推理能力。TF-IDF 原理参考 [scikit-learn 文本特征文档](https://scikit-learn.org/stable/modules/feature_extraction.html#text-feature-extraction)；实现仅使用 Python 标准库。

相似记录的实际/预计工时比按匹配分加权取中位数，回忆数据权重减半。局部权重为 `有效匹配权重之和 / (有效匹配权重之和 + 2)`，其余仍采用总体历史效率。没有匹配时回退总体效率；没有可靠历史记录时使用初始估时。任务结果包含 `history_calibration`、`history_calibration_note`、`similar_history_weight` 和 `similar_history`，界面可展开依据并查看对应原记录。上述阈值是可解释的初始参数，需后续用实际任务验证和调整。

## 当前预测与组合风险算法

进行中任务的剩余工时预测暂时采用可解释的两部分信号：

1. 根据“已投入工时 / 已完成比例”反推完成该任务的总工时。
2. 使用相似历史记录与总体可靠记录的 `实际工时 / 预计工时` 比率融合值，校准当前任务的预计总工时。

两者按进度逐渐增加前者权重，并保留历史效率作为修正，避免刚开始记录时的偶然值影响过大。系统还会依据实际进度是否存在、任务完成比例、可靠历史样本数量与数据精度，给预测标注可信度。

风险分析包含两层：第一层按每个截止日期累计所有未完成任务的剩余工时，再与该日期前扣除缓冲后的总可用时间比较；第二层按 EDF（Earliest Deadline First）逐日分配缓冲后的可用工时，同一截止日期按优先级排序，从而计算每项任务的预计完成日期与截止时未排完的工时。多个任务共同占用同一容量。当前历史关联依据课程与标题文字，没有使用大模型做难度判断；后续可积累显式任务类型和用户反馈后改进。
