课程允许学生完全自定义选题。本项目选择学业负荷雷达，属于个人效率工具：它帮助同时承担多门课程、实验和项目任务的学生判断截止日期前的累计工作量是否超过个人可用时间。该选题不替代教学平台，也不评价学习成绩。\n15: 1.2 问题陈述\n16: 普通待办工具通常按任务分别显示截止日期。学生真正面临的是共享时间容量：一个较晚截止的任务需要与此前所有未完成任务竞争同一段时间。若只比较单个任务的工时与截止日期前时间，就会低估多个任务叠加后的风险。\n17: 进行中任务还有第二个不确定性。最初填写的预计工时会随任务推进而失真，系统需要结合已经投入的时间、当前完成比例和过去任务的实际与预计偏差，重新估算剩余工时。估算必须说明使用了哪些数据，不能只给出无法解释的风险标签。\n18: 1.3 需求结论\n19: 系统必须把同一截止日期前的全部未完成任务纳入累计负荷，而不是逐条独立判断。\n20: 系统必须允许补录进行中任务和历史任务，避免只能从启用系统当天开始积累数据。\n21: 系统必须区分批量导入与批量处理；批量处理指一次重新分析已经填写的全部任务。\n22: 系统必须显示剩余工时、累计负荷、可用容量和计算依据，便于用户复核。\n23: 2 目标用户与使用场景\n25: 2.1 核心场景\n27: 3 目标 假设与范围\n28: 3.1 产品目标与成功指标\n30: 3.2 关键假设\n31: 用户能给出大致合理的预计工时，并愿意在任务推进后更新投入时间和进度。\n32: 完成比例是主观数据，因此只作为估算信号，并保留历史效率权重。\n33: 第一阶段按设备本地日期计算，不处理跨时区协作。\n34: 历史任务不足时不得假装模型已经个性化，默认历史效率系数为 1.0。\n35: 3.3 纳入范围\n36: 普通 进行中和历史任务的录入与保存；历史和进行中任务 CSV 导入。\n37: 个人可用时间 缓冲比例 跟踪窗口和提前完成阈值设置。\n38: 剩余工时预测 累计容量分析 风险评分和解释。\n39: 批量处理已填写任务 完成跟踪 近期统计与缓冲建议。\n40: 本地 SQLite 持久化 响应式网页和基础错误提示。\n41: 3.4 范围外事项\n42: 多用户账号 组织权限 学校统一身份认证和云端同步。\n43: 自动读取教务系统 邮件 日历或第三方待办平台。\n44: 自动替用户调整截止日期 删除任务或做学业决策。\n45: 使用大模型直接判断任务难度；该能力需要足够分类样本和隐私评估后再立项。\n46: 原生移动端应用 多人协作排期和实时通知。\n47: 4 功能需求\n49: FR-01 普通任务管理\n51: 用户能够创建普通任务并查看其状态。普通任务用于尚未开始或暂不记录进度的课程任务。\n53: FR-02 进行中任务录入\n55: 用户能够录入在启用系统之前已经开始但尚未完成的任务，使已投入工时和完成比例进入剩余负荷计算。\n57: FR-03 历史任务补录\n59: 用户能够补录系统启用前已经完成的任务，以增加个性化估时和完成表现的样本。\n61: FR-04 个人容量与缓冲设置\n63: 用户设置工作日和周末每天可用于任务的时间，以及为突发情况保留的安全缓冲比例。缓冲不是额外时间，而是从理论容量中扣除的比例。\n65: FR-05 剩余工时预测\n67: 系统使用进度反推与历史效率两类信号估算进行中任务的剩余工时，并返回预测方法。算法规则见第 5 章。\n69: FR-06 累计组合风险\n71: 系统评估某截止日期时，必须累计所有截止日期不晚于该日期的未完成任务剩余工时，避免遗漏此前需要完成的任务。\n73: FR-07 批量处理当前任务\n75: 批量处理是对数据库中已经填写的全部任务执行一次统一重算与汇总，不等同于批量导入。\n77: FR-08 完成与跟踪模式\n79: 开启跟踪模式后，用户标记完成任务时必须填写实际工时；系统记录完成时间并按提前阈值分类。\n81: FR-09 近期统计与缓冲建议\n83: 系统在指定滚动窗口内统计按时率 实际与预计工时中位比 提前和临近截止效率，并给出缓冲比例建议。截止前效率提升只用于解释，不能成为自动降低缓冲的单一依据。\n85: FR-10 CSV 批量导入\n87: 系统支持分别导入历史任务和进行中任务，用于快速补齐已有数据。该能力与 FR-07 的批量处理相互独立。\n89: FR-11 仪表盘与持久化\n91: 系统通过浏览器显示任务 容量和近期统计，并使用 SQLite 保存数据。正常重启后数据应保留。\n93: FR-12 任务删除和错误反馈\n95: 用户能够删除错误任务。所有失败操作必须提供可理解的原因，避免静默失败。\n97: 5 业务规则与核心算法\n98: 5.1 可用容量与缓冲\n99: 在今天至截止日期的闭区间内，工作日使用 weekday_hours，周末使用 weekend_hours。理论容量为每日容量之和。可用容量 C 等于理论容量乘以 (1 - B)，其中 B 是缓冲比例，限制在 0 至 0.8。截止日期早于今天时天数按 0 处理。\n100: 5.2 历史效率系数\n101: 对状态为 done、actual_hours 有效、estimated_hours 大于 0 且 data_precision 不为 rough 的任务，计算 actual_hours / estimated_hours。历史效率系数 H 取这些比值的中位数；没有可靠样本时 H=1.0。中位数用于降低极端任务的影响。\n102: 5.3 进行中任务预测\n104: 符号定义：E 为预计总工时，S 为已投入工时，P 为 0 至 0.99 的完成比例，R 为预测剩余工时。进度越高，进度反推的权重越高，但上限为 0.75，避免主观进度完全覆盖历史证据。\n105: 5.4 组合负荷与风险等级\n106: 对截止日期 d，累计负荷 L(d) 是所有未完成且截止日期不晚于 d 的任务剩余工时之和。负荷比 Q=L(d)/max(C(d),0.1)。若任务已逾期或 Q>1，风险为高；若 Q≥0.7 或剩余天数不超过 2，风险为中；其余为低。\n107: 风险分数由容量压力、截止紧迫度和优先级构成：容量部分为 min(65,Q×50)；剩余不超过 2 天加 20 分，不超过 5 天加 10 分；优先级 3 加 15 分，优先级 2 加 7 分；总分上限 100。风险等级以业务规则为准，分数用于排序。\n108: 5.5 缓冲调整规则\n109: 完成样本少于 5 个时不调整。\n110: 按时率低于 80% 估时中位比大于 1.1 或逾期率高于 20% 时增加缓冲的证据增强。\n111: 按时率至少 90% 估时中位比小于 0.95 且没有逾期时可建议降低缓冲。\n112: 单次变化限制在正负 5 个百分点，最终范围为 5% 至 40%。\n113: 临近截止效率提高只显示提醒，不因此直接降低缓冲。\n114: 6 数据需求\n116: 6.1 CSV 格式\n117: CSV 使用 UTF-8 编码和首行字段名。英文和约定中文字段名均可识别。日期使用 YYYY-MM-DD，日期时间使用 YYYY-MM-DDTHH:MM。数值字段不得带小时或百分号等单位文本。导入结果必须保留批次编号、成功记录编号和失败行号。\n118: 6.2 输出数据\n120: 7 接口与运行环境\n122: 7.1 环境与依赖\n123: 服务端使用 Python 标准库 ThreadingHTTPServer 和 SQLite，不要求额外 Python 包。\n124: 客户端使用 HTML CSS
